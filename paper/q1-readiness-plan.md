## Research thesis

The paper will test one claim:

> A dataframe runtime can choose between TypeScript and WebAssembly more reliably when dispatch accounts for operation shape, algorithm, conversion cost, reusable numeric storage, and runtime-specific calibration.

API breadth, browser portability, package size, and pandas familiarity support this claim. They are not substitutes for it.

## Implementation sequence

### 1. Adaptive execution module

Create one deep module at the TypeScript/Wasm seam. Its interface accepts an operation description and numeric storage facts, then returns `typescript` or `wasm` with a reason code. DataFrame and GroupBy callers must not encode their own thresholds.

The implementation will cover:

- Wasm availability and forced TypeScript mode.
- Full sort versus bounded top-k selection.
- Mask compaction disabled by default until new evidence reverses the result.
- Fused group-by guarded by row count, plan count, and reusable typed columns.
- Runtime calibration data loaded as versioned plain data, not hard-coded comments.
- Decision tracing for benchmark and paper artifacts.

### 2. Typed-column reuse

Attach an internal numeric-column cache to a DataFrame generation. Mutating operations invalidate the generation. Read-only operations may reuse typed columns. The cache stays behind the adaptive module's interface and is tested through observable dispatch and result behavior.

### 3. Differential pandas oracle

Add a JSON protocol shared by Bun and Python runners. Each case records inputs, operation, result values, labels, dtypes, warnings or errors, and whether inputs changed. A normalizer must preserve meaningful differences rather than coercing both systems to generic JSON.

### 4. Experiment runner

Replace single-process summaries with a controller that launches fresh child processes. The controller randomizes balanced blocks, records every sample, validates output hashes, and writes process-level medians. A separate analysis command computes paired ratios and bootstrap intervals.

Default paper settings:

- 30 fresh processes per system and workload.
- Calibrated in-process iterations with raw ordered samples retained.
- Row counts of 1,000, 10,000, 100,000, 1,000,000, plus the largest safe stress size.
- Widths of 8, 32, and 128 columns where the operation permits.
- Missingness of 0%, 1%, and 10%.
- Low, square-root, and high group cardinality.
- Join shapes covering one-to-one, one-to-many, many-to-many, and unmatched keys.

### 5. Memory telemetry

Record process RSS before construction, after construction, at peak operation use, and after result materialization. Record JavaScript heap data when the runtime exposes it and Wasm memory pages before and after each kernel. Report retained memory and peak process memory as different quantities.

### 6. Browser core

Split filesystem and process features from the computation entry. Load Wasm from bytes or a URL through an asynchronous adapter. Run browser work in a Web Worker and verify sorting, grouping, filtering fallback, and serialization. "No server" means no application backend; static assets still require normal browser delivery or an offline package.

### 7. Release artifact

Provide one local reproduction command, a clean package check, deterministic manifests, and an archive assembly command. Publication to npm and DOI creation require the author's authenticated accounts and remain explicit release steps.

### 8. Manuscript regeneration

Generate every number and table from artifact JSON. The final manuscript must report negative results, unsupported comparisons, confidence intervals, and memory data. A humanizer and unslop pass follows the technical freeze, not each intermediate benchmark run.
